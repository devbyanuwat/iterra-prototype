# มาตรฐานที่โครงการ ITERRA อ้างอิง

จัดทำ 2026-10-12 สำหรับทีมพัฒนา

โครงการอ้างอิงแนวทางของมาตรฐาน ISO 4 ฉบับ แต่ละฉบับใช้เป็นรายการตรวจสั้น ๆ ไม่ได้ทำตามกระบวนการเต็มของมาตรฐาน

## ข้อจำกัดที่ต้องรู้ก่อนใช้เอกสารนี้

- เนื้อหาเขียนจากความรู้ทั่วไปเกี่ยวกับโครงสร้างและหลักการของมาตรฐาน ยังไม่ได้เทียบกับตัวมาตรฐานฉบับจริง
- ยังไม่ได้ยืนยันชื่อเต็มและรุ่นปีล่าสุดของแต่ละฉบับ
- ตัวมาตรฐานมีลิขสิทธิ์และต้องซื้อ เอกสารนี้ไม่ยกข้อความหรือเลขข้อ ถ้าต้องอ้างเลขข้อ ต้องมีฉบับจริง
- โครงการไม่มีการตรวจรับรอง

## คำที่ใช้ได้ และคำที่ห้ามใช้

| ใช้ได้ | ห้ามใช้ |
| --- | --- |
| อ้างอิงแนวทางของ ISO/IEC 25010 | ได้รับการรับรอง ISO |
| ใช้รายการตรวจที่อิงจาก ISO/IEC 27002 | เป็นไปตามมาตรฐาน ISO |
| รูปแบบวันที่ตาม ISO 8601 | ISO certified |

รูปแบบวันที่ตาม ISO 8601 เป็นข้อเดียวที่พูดได้ว่า "ตาม" เพราะตรวจได้จากข้อมูลจริงทุกค่า

## สรุป

| มาตรฐาน | เรื่อง | ใช้กับ | หลักฐาน |
| --- | --- | --- | --- |
| ISO/IEC/IEEE 29148 | วิศวกรรม requirement | ทะเบียน requirement | ทะเบียนใน `docs/pm/` |
| ISO/IEC 25010 | แบบจำลองคุณภาพซอฟต์แวร์ | ข้อกำหนดด้านคุณภาพ และแผนทดสอบ | ผลทดสอบรายหมวด |
| ISO/IEC 27002 | มาตรการความมั่นคงปลอดภัย | server, login, อัปโหลดไฟล์, สำรองข้อมูล | รายการตรวจที่ลงชื่อก่อนขึ้นจริง |
| ISO 8601 | รูปแบบวันที่และเวลา | ฐานข้อมูล, API, ชื่อไฟล์, ทะเบียนของ PM | ตรวจจากข้อมูลจริง |

## 1. ISO/IEC/IEEE 29148: requirement

**หยิบมาใช้**: requirement ที่ดีต้องผ่านเกณฑ์ของโครงการ 6 ข้อ

1. จำเป็น: ถ้าตัดออก ผู้ใช้หรือร้านเสียอะไรบางอย่าง
2. ไม่กำกวม: อ่านแล้วตีความได้ทางเดียว
3. ข้อเดียวเรื่องเดียว: ไม่มีคำว่า "และ" ที่ซ่อน 2 ความต้องการ
4. ทำได้จริง: ภายในเวลา คน และเครื่องที่มี
5. ตรวจสอบได้: บอกได้ว่าทดสอบอย่างไรจึงถือว่าผ่าน
6. ตามรอยได้: รู้ว่าใครขอ เมื่อไร และงานชิ้นไหนทำให้ข้อนี้สำเร็จ

**ข้อมูลที่ทุก requirement ต้องมี**

| ช่อง | ตัวอย่าง |
| --- | --- |
| รหัส | `REQ-014` |
| ข้อความ | พนักงานเพิ่มบทความพร้อมรูปได้เองจากหน้าหลังบ้าน |
| ที่มา | คุณอนุวัชร, 2026-10-12, แชต |
| เหตุผล | ร้านต้องแก้เนื้อหาเองโดยไม่รอทีมพัฒนา |
| ลำดับความสำคัญ | ต้องมี / ควรมี / มีก็ดี |
| สถานะ | เสนอ / ตกลงแล้ว / กำลังทำ / ทำแล้ว / ยกเลิก |
| วิธีตรวจ | ทดสอบ / สาธิต / ตรวจเอกสาร |
| หลักฐาน | ลิงก์ commit, PR หรือผลทดสอบ |
| ประวัติการเปลี่ยน | วันที่ ใครขอเปลี่ยน เปลี่ยนจากอะไรเป็นอะไร |

**ด่านตรวจ**: requirement ที่ยังไม่มีวิธีตรวจ ห้ามเปลี่ยนสถานะเป็น "ตกลงแล้ว"

## 2. ISO/IEC 25010: คุณภาพ

**หยิบมาใช้**: หมวดคุณภาพ 8 หมวด เป็นหัวข้อของข้อกำหนดด้านคุณภาพและของแผนทดสอบ มาตรฐานฉบับปรับปรุงเปลี่ยนชื่อบางหมวดและเพิ่มหมวด ต้องยืนยันกับฉบับจริง

เกณฑ์ในตารางเป็นข้อเสนอ ยังไม่ได้ตกลงกับลูกค้า และยังไม่ได้วัดค่าจริง

| หมวด | เกณฑ์ของ ITERRA | ตรวจด้วย |
| --- | --- | --- |
| ฟังก์ชันครบและถูก | requirement ที่สถานะ "ทำแล้ว" ทุกข้อมีกรณีทดสอบที่ผ่าน | ทะเบียน requirement |
| ประสิทธิภาพ | ภาพหลักของหน้าแรกขึ้นภายใน 2.5 วินาทีบนมือถือ, อัปโหลด PDF 18 MB สำเร็จโดยไม่หมดเวลา | วัดบน server จริง |
| ความเข้ากันได้ | Chrome, Safari, Edge รุ่นปัจจุบันและรุ่นก่อนหน้า, Safari บน iOS, Chrome บน Android | ทดสอบด้วยมือ |
| การใช้งาน | พนักงานเพิ่มบทความพร้อมรูปได้เองภายใน 10 นาทีโดยไม่ถามทีม, ไม่มีหน้าล้นจอ, ปุ่มกดได้ไม่น้อยกว่า 44 พิกเซล, ใช้แป้นพิมพ์ได้ | ทดลองใช้กับพนักงานจริง, `npm run check:overflow` |
| ความน่าเชื่อถือ | สำรองข้อมูลทุกวัน, กู้คืนสำเร็จอย่างน้อย 1 ครั้งก่อนตรวจรับ, มีตัวเฝ้าเมื่อเว็บล่ม | บันทึกการกู้คืน |
| ความปลอดภัย | ผ่านรายการตรวจในหมวด 3 ทุกข้อ | รายการตรวจที่ลงชื่อ |
| การบำรุงรักษา | `npx tsc --noEmit` ผ่าน, สคริปต์ `check:*` ผ่าน, ทำตาม `design.md`, ทุกรอบ deploy มี PR ที่ผ่านการรีวิว | ประวัติ PR |
| การย้ายระบบ | มีเอกสารขั้นตอน deploy, สร้าง server ใหม่ได้จากเอกสารกับชุดสำรอง, มีรายการค่าตั้งที่ต้องใช้ | ทำตามเอกสารบนเครื่องเปล่า 1 ครั้ง |

## 3. ISO/IEC 27002: ความมั่นคงปลอดภัย

**หยิบมาใช้**: แนวคิดเรื่องมาตรการควบคุม จัดเป็นรายการตรวจของโครงการ ทุกข้อต้องผ่านก่อนขึ้น server จริง

### บัญชีและสิทธิ์

- [ ] พนักงานแต่ละคนมีบัญชีของตัวเอง ไม่ใช้บัญชีร่วม
- [ ] รหัสผ่านยาวไม่น้อยกว่า 12 ตัวอักษร และเก็บแบบ hash ที่ออกแบบมาสำหรับรหัสผ่าน
- [ ] login ผิด 5 ครั้งติดกัน ล็อก 15 นาที
- [ ] ทุกหน้าและทุก API ของหลังบ้านตรวจสิทธิ์ที่ฝั่ง server
- [ ] session หมดอายุเมื่อไม่ใช้งาน และออกจากระบบได้จริง
- [ ] เมื่อพนักงานลาออก ปิดบัญชีภายในวันเดียวกัน
- [ ] หน้า 1Panel ใช้รหัสผ่านที่แข็งแรง ไม่ใช้พอร์ตเริ่มต้น และ SSH เข้าด้วยกุญแจเท่านั้น

### ความลับ

- [ ] ไม่มีรหัสผ่าน กุญแจ หรือ connection string ใน repo
- [ ] ไฟล์ `.env` ไม่ถูก commit และมีไฟล์ตัวอย่างที่ไม่มีค่าจริง
- [ ] มีรายการว่าความลับแต่ละตัวอยู่ที่ไหน ใครเข้าถึงได้

### การอัปโหลดไฟล์

- [ ] รับเฉพาะชนิดที่กำหนด ตรวจจากเนื้อไฟล์ ไม่ใช่จากนามสกุล
- [ ] จำกัดขนาดที่ฝั่ง server
- [ ] ตั้งชื่อไฟล์ใหม่ทุกครั้ง ไม่ใช้ชื่อที่ผู้ใช้ส่งมา
- [ ] ไฟล์ที่อัปโหลดรันเป็นโปรแกรมไม่ได้
- [ ] การแปลง PDF เป็นภาพทำในกระบวนการที่จำกัดหน่วยความจำและเวลา

### การส่งข้อมูล

- [ ] ใช้ HTTPS เท่านั้น
- [ ] คุกกี้ของ session ตั้ง `Secure`, `HttpOnly` และ `SameSite`

### สำรองข้อมูล

- [ ] สำรองฐานข้อมูลและไฟล์ที่อัปโหลดทุกวัน
- [ ] มีสำเนาอยู่นอกเครื่อง server
- [ ] ทดสอบกู้คืนจากชุดสำรองสำเร็จอย่างน้อย 1 ครั้งก่อนตรวจรับ
- [ ] กำหนดว่าเก็บชุดสำรองกี่วัน

### บันทึกและเฝ้าระวัง

- [ ] บันทึกการ login ทั้งสำเร็จและไม่สำเร็จ
- [ ] บันทึกว่าใครเพิ่ม แก้ ลบ เนื้อหาอะไร เมื่อไร
- [ ] มีตัวเฝ้าที่แจ้งเมื่อเว็บล่มหรือดิสก์ใกล้เต็ม

### การอัปเดต

- [ ] อัปเดตระบบปฏิบัติการ 1Panel และแพ็กเกจของโครงการอย่างน้อยเดือนละครั้ง
- [ ] ตรวจช่องโหว่ของแพ็กเกจก่อนทุกรอบ deploy

### ผู้ให้บริการและเจ้าของบัญชี

- [ ] มีรายการผู้ให้บริการทุกเจ้า: โดเมน, server, อีเมล, ที่เก็บโค้ด
- [ ] บัญชีของบริการที่ใช้กับเว็บจริงอยู่ในชื่อของร้าน ไม่ใช่บัญชีส่วนตัวของผู้พัฒนา

ข้อสุดท้ายยังไม่ผ่าน: ตอนนี้ repo อยู่ใต้บัญชี GitHub `devbyanuwat` และเว็บต้นแบบอยู่ใต้บัญชี Vercel `anuwats-projects-668275de` (ตรวจ 2026-10-12)

### สิ่งที่ไม่ใช่ ISO แต่ต้องทำ

กฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA) เป็นกฎหมาย ไม่ใช่มาตรฐาน ISO นโยบายความเป็นส่วนตัวต้องผ่านการตรวจทางกฎหมายก่อนที่แบบฟอร์มติดต่อจะเริ่มเก็บข้อมูลจริง

## 4. ISO 8601: วันที่และเวลา

- ฐานข้อมูลและ API ใช้เวลา UTC: `2026-10-23T02:30:00Z`
- วันที่ที่ไม่มีเวลา: `2026-10-23`
- แสดงผลตามเขตเวลา Asia/Bangkok หน้าจอภาษาไทยแสดงปี พ.ศ. การแปลงทำที่ชั้นแสดงผลเท่านั้น
- ชื่อไฟล์ที่มีวันที่ขึ้นต้นด้วย `YYYY-MM-DD` ตามที่ใช้อยู่ใน `docs/superpowers/`
- ทะเบียนของ PM เขียนวันที่แบบ `2026-10-12` ส่วนเอกสารที่ส่งลูกค้าเขียนเป็นวันที่ไทยแบบเต็ม

รหัสภาษา `th` และ `en` ที่ใช้ในโค้ดเป็นไปตาม ISO 639-1 อยู่แล้ว ไม่ได้นับเป็นฉบับที่ 5 เพราะไม่มีงานต้องทำเพิ่ม

## มาตรฐานที่พิจารณาแล้วไม่ใช้ในรอบนี้

ISO 9241 (การใช้งาน), ISO/IEC 40500 (การเข้าถึงเว็บ), ISO/IEC/IEEE 29119 (เอกสารทดสอบ), ISO 31000 (ความเสี่ยง), ISO 21502 (การบริหารโครงการ)

เกณฑ์การเข้าถึงที่ใช้อยู่แล้ว (contrast, ขนาดปุ่ม, แป้นพิมพ์) ยังอยู่ใน `design.md` ตามเดิม
